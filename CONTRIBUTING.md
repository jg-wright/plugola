# Contributing to Plugola

Thanks for your interest. This guide covers setting up the repo, the day-to-day
workflow, the conventions CI and the commit hooks enforce, and how releases
work.

## Getting set up

You'll need **Node.js 24 or later** (the repo pins 26 in [`.nvmrc`](.nvmrc), so
run `nvm use` if you have nvm) and **npm**. The repo uses npm workspaces, so
don't use yarn or pnpm.

```sh
git clone https://github.com/jg-wright/plugola.git
cd plugola
npm ci          # install, link workspaces, and set up git hooks (husky)
npm run build   # compile every package
npm test        # run every package's tests
```

**Always build before testing.** Packages import each other's compiled `dist/`
output rather than their source. If one package's tests fail because another
package seems out of date, run `npm run build` again.

## Repository layout

```
packages/
  <name>/
    src/            source (TypeScript)
    test/           vitest specs
    dist/           build output (generated, not committed)
    README.md       the package's user-facing docs
    CHANGELOG.md    generated by release-please; don't edit
    package.json
    tsconfig.json
tsconfig.json                   project references to every package
release-please-config.json      release configuration, one entry per package
.release-please-manifest.json   current version of each package
plugola.code-workspace          VS Code multi-root workspace
```

Each directory in `packages/` is a separate npm package, `@plugola/<name>`.
Packages depend on each other through ordinary semver ranges (for example,
`@plugola/plugin-manager` depends on `@plugola/graph`), and npm workspaces link
them locally. TypeScript project references in the root
[`tsconfig.json`](tsconfig.json) build them in the right order.

For a map of the packages and how they fit together, see the
[README](README.md#packages).

## Everyday commands

Run these from the repo root:

| Command                                | What it does                                             |
| -------------------------------------- | -------------------------------------------------------- |
| `npm run build`                        | `tsc --build` across every package (incremental).        |
| `npm start`                            | Same, in watch mode.                                     |
| `npm test`                             | Runs `vitest --run` in every package.                    |
| `npm test --workspace @plugola/<name>` | Tests a single package.                                  |
| `cd packages/<name> && npx vitest`     | Tests a single package in watch mode.                    |
| `npx vitest -u` (inside a package)     | Updates snapshots, including inline snapshots.           |
| `npm run clean`                        | Deletes all build output, for when the build gets stuck. |

Opening [`plugola.code-workspace`](plugola.code-workspace) in VS Code gives you
one folder per package.

## Code conventions

The TypeScript compiler, Prettier and CI enforce most of these, but knowing
them up front saves a round trip.

- **ESM only.** Every package is `"type": "module"` with `nodenext` module
  resolution, so relative imports **must** include the `.js` extension, even in
  `.ts` files:

  ```ts
  import Graph from '../src/Graph.js'
  ```

- **Strict TypeScript**, plus `noUnusedLocals`, `noUnusedParameters`,
  `noImplicitOverride` and `noImplicitReturns`. Unused code fails the build.
- **Formatting** is handled by [Prettier](prettier.config.js): no semicolons,
  single quotes. A pre-commit hook formats staged files for you.
- **Style.** Packages usually have a main class exported as the `default`
  export, and use `#private` fields for internals.
- **Tests** use vitest (`import { test, expect } from 'vitest'`) and lean
  heavily on `toMatchInlineSnapshot`. Some packages also have type-level tests
  in `*.test-d.ts` files.
- **Docs.** If you change a package's public API, update that package's
  `README.md` in the same pull request.

## Commit messages

Commits must follow [Conventional Commits](https://www.conventionalcommits.org/).
A commit-msg hook (commitlint) rejects anything else. The type decides how a
release bumps the version, so pick it carefully:

| Type                                              | Release effect        |
| ------------------------------------------------- | --------------------- |
| `fix:`                                            | patch release         |
| `feat:`                                           | minor release         |
| `feat!:` / `fix!:` or a `BREAKING CHANGE:` footer | major release         |
| `docs:`, `test:`, `refactor:`, `chore:`, `ci:` …  | no release on its own |

A scope naming the package is encouraged, for example
`fix(message-bus): drop unused dependency`. Release-please works out which
package a commit belongs to from the files it touches, so keep each commit to a
single package where you can.

## Pull requests

1. Branch from `master`.
2. Make your change with tests, and update the package's README if its API
   changes.
3. Check that `npm run build && npm test` passes locally.
4. Open a pull request. CI runs `npm ci && npm run build && npm test` on Node 24
   and 26, and both must pass.

## Releases

Releases are fully automated with
[release-please](https://github.com/googleapis/release-please). **Don't bump
versions or edit `CHANGELOG.md` by hand.**

1. When commits land on `master`, release-please opens or updates a release pull
   request that bumps the affected packages and writes their changelogs.
2. Merging that pull request creates a GitHub release and a tag for each package
   (for example `logger-v5.0.4`).
3. Each release triggers [`release.yml`](.github/workflows/release.yml), which
   builds and publishes that package to npm using trusted publishing.

Each package is versioned and released independently.

## Adding a new package

Model the new package on an existing small one, such as
[`packages/store`](packages/store). There's also a scaffolding prompt for AI
assistants at
[`.github/prompts/new-package.prompt.md`](.github/prompts/new-package.prompt.md).

Besides the package's own files (`package.json`, `tsconfig.json`,
`test/tsconfig.json`, `src/`, `test/`, `README.md` and `LICENSE`), register it in
each of these lists, keeping each list in alphabetical order:

- [`tsconfig.json`](tsconfig.json): add `{ "path": "packages/<name>" }` to
  `references`.
- [`release-please-config.json`](release-please-config.json): add
  `"packages/<name>": {}` to `packages`.
- [`.release-please-manifest.json`](.release-please-manifest.json): add
  `"packages/<name>": "0.0.0"`.
- [`plugola.code-workspace`](plugola.code-workspace): add a folder entry.
- The package table in the root [README](README.md#packages).

The build and tests pass even if you miss the release-please entries, but the
package will never be released. Run `npm install` to link the new workspace,
then `npm run build` and `npm test --workspace @plugola/<name>`.

## Reporting bugs and asking questions

Open an [issue](https://github.com/jg-wright/plugola/issues). For bugs, include
the package name and version, your runtime (browser or Node.js version), and a
minimal reproduction if you can.
